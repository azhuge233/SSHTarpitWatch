# 通知

[← 返回 README](../README.md) ｜ [English](en/notifications.md)

v1 的通知渠道为 Telegram（其他渠道仅预留扩展接口，未实现）。

## 通知长什么样

默认**每条连接只在断开时收到一条通知**——连接期收集到的信息（客户端身份串、本机端口、连接时刻）都会并进这一条里：

```
🕳 home-vps · SSHTarpitWatch · 连接断开
来源：203.0.113.7:54321 → 本机 :2222
客户端：SSH-2.0-libssh2_1.11.0
地区：中国 · 江苏省 · 南京市 (CN)        ← 开启 IP 地区解析后出现（见「配置」）
ISP：电信 (AS4134)                          ← 组织名 + AS 号（号可点按复制）；库只给其一就只显示其一
时间：2026-10-11 09:02:03 (UTC+08:00)
停留：0 小时 12 分 39 秒
发出：4096 字节
该 IP 今日第 3 次
#中国 #CN #江苏省 #南京市 #AS4134 #电信    ← 地区 + ISP 标签（GeoIP 启用时自动追加；点标签可筛历史消息）
```

- `时间` = **连接建立**的时刻（不是断开的时刻）；`停留` 是这次连接被吊住的时长。
- 末尾的**标签行**在 GeoIP 启用时自动追加（无配置开关）：点标签即可筛出同国家/省/市/运营商的消息；**ISP 行里的 AS 号点按可复制**；未启用 GeoIP 时整行不出现。
- 昵称留空（`nickname: ""`）时显示系统主机名。
- 客户端未上报身份串时，`客户端` 一行显示 `—`。
- 时间为服务器本地时间（含 UTC 偏移）。

想在连接建立时先收到一条（连接条 + 断开条共两条），把 `notifications.filter.on_connect` 设为 `true`：

```
🕳 home-vps · SSHTarpitWatch · 新连接
来源：203.0.113.7:54321 → 本机 :2222
客户端：SSH-2.0-libssh2_1.11.0
时间：2026-10-11 09:02:03 (UTC+08:00)
该 IP 今日第 3 次
```

测试通知（`--test-notify` 发出，与真实事件区分）：

```
🕳 home-vps · SSHTarpitWatch · 测试通知
时间：2026-10-11 09:02:03 (UTC+08:00)
```

## 只通知停留够久的连接

`notifications.filter.min_duration_seconds`（默认 `0` = 不过滤）：只有停留时长**达到该秒数**的连接才会通知。扫描器“连上就走”的探测会被自动忽略；配合默认的“只在断开时通知一条”，日常通知量从“每次探测”降到“每次真正的纠缠”。

- 判定用**断开时刻**的配置值——改完配置（`SIGHUP` 重载）立刻对已经挂着的连接生效。
- **时长精度**：对端关闭（FIN/RST）被**即时感知**——首行读取结束后程序会挂一个待读，停留时长即真实值（实测：2 秒断开记 2.005 秒，0.3 秒记 0.302 秒），据此可放心把阈值设小；唯一例外是**无 FIN 的静默消失**（网络中断等），那种情况仍在下一次慢滴写入时才发现（差值 ≤ 一个 `server.delay_ms`）
- 被时长过滤掉的连接**不占用**该 IP 的冷却额度，也不影响该 IP 后续连接的通知。
- 但它**仍会计入**“该 IP 今日第 N 次”。

## 去重与限速

- **每 IP 冷却**（`notifications.throttle.per_ip_seconds`，默认 300 秒）：同一 IP 在冷却期内只报一次；0 = 关闭。
- **开启连接条时**（`filter.on_connect=true`）：断开条跟随其连接条——某次连接的连接通知被冷却压掉时，它的断开通知也不发。未开启时（默认），断开条按每 IP 冷却独立判定。
- **中途开启连接条**（经 `SIGHUP` 把 `filter.on_connect` 由 `false` 改为 `true`）时：**已经挂着**的存量连接，其连接条当时就没发过，按跟随规则它们的断开条也不补发（日志里记为 `suppressed_dedup`）；开启之后**新建立**的连接正常两条。
- **全局限速**（`notifications.throttle.max_per_minute`，默认 3）：所有通知共用一个令牌桶——平均每分钟最多 3 条、突发上限 3 条。
- **队满丢新**：通知经有界内存队列（1024 条）发送，队列满时丢弃新条目并记日志——绝不拖慢困住逻辑。
- 发送失败自动重试（最多 3 次：退避 2 秒 / 10 秒 / 30 秒；Telegram 返回 429 时按其 `retry_after` 等待）；最终失败只记日志。
- 冷却窗口与“今日第 N 次”计数**只存在内存中**：重启进程后两者清零（同一 IP 会重新上报一次，计数从头开始）。
